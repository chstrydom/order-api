# AI Tool Usage

Tools used: Claude (Anthropic), via the Claude web interface.

The table below summarises AI assistance used during project setup, requirements analysis, design documentation, implementation review, testing and containerisation. Prompts and responses are summarised rather than reproduced verbatim.

| Tool | Prompt Given | Response Received | How the output was used |
|---|---|---|---|
| Claude | Review the proposed data model and API contract for order intake, retrieval, stock lookup, and daily reporting. | Identified design considerations around order identity, stored order-line prices, response behaviour, and report definitions. | Used to refine the proposed entities, endpoint list, and documented assumptions. |
| Claude | Review the proposed background stock-processing approach, including temporary worker interruption and recovery. | Highlighted the need for durable pending work, safe concurrent stock updates, transactional processing, and protection against repeated stock deductions. | Used to document the database-backed work queue, transaction requirements, and recovery test scenarios. |
| Claude | Critically review the solution design and challenge unresolved business rules and scope decisions. | Identified ambiguities around insufficient stock, duplicate submissions, order status, revenue reporting, and out-of-scope functionality. | Used to clarify the intended rejection policy, idempotency behaviour, report semantics, and remaining implementation decisions. |
| Claude | Review idempotency implementation, transaction handling, and automated tests. | Reviewed chosen and rejected implementation approaches, SQL queries and pytest test cases, with follow-up questions about design decisions and expected behaviour. | Used as an implementation aid and technical sounding board. Reviewed and integrated suggested changes, ran the full test suite, investigated test failures and verified the resulting behaviour. AI-generated suggestions were evaluated rather than accepted uncritically. |
| Claude | Requested guidance on running a newly added `scripts/seed_and_burst.py` demonstration script and a corrected version of the script. | Reviewed the existing script and identified issues involving repeatability, inventory resets during seeding, and pause-sentinel cleanup. Provided refactored snippets with unique run identifiers, non-destructive product seeding, and safer pause/resume handling. | Used the AI-assisted refactoring as the basis for updating the demonstration script. The script remains a project-owned implementation and is run locally against the API and PostgreSQL database. |
| Claude | Review the worker runner's pause-sentinel behaviour (`WORKER_PAUSE_SENTINEL`) and wire it into the Docker setup and documentation for the interruption demonstration. | Reviewed the polling loop and its tests (pause holds orders as `RECEIVED`, removing the sentinel lets the worker catch up, database errors are retried, shutdown is graceful). Recommended that the sentinel check stay in the polling loop and not in `process_one_order`. Provided a Compose setup that mounts `./worker_control` into the worker, `.env.example` and `.gitignore` entries, and README and design-document wording. | The runner and sentinel code were written by me. Claude's suggestions were reviewed before use, and I ran the tests and the pause/resume demonstration locally. I confirmed that `scripts/seed_and_burst.py` uses the same sentinel path as the worker. |
